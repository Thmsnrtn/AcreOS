# Runbook: GDPR / CCPA Data Subject Access Request (DSAR) Fulfilment

**Severity:** P1 — Legal SLA at risk
**Owner:** Founder / legal / privacy officer
**Time to first response:** 24 hours

---

## Symptom
- Data Subject Access Request received via support@ or legal@ email
- Request references GDPR (EU) with 30-day SLA or CCPA (CA) with 45-day SLA
- Requestor claims to be a customer or user of AcreOS
- Requestor asks for "all data you hold about me"

---

## Diagnose
1. Create a `dsar_requests` row in the DB:
   ```sql
   INSERT INTO dsar_requests (id, requester_email, request_date, requested_at, jurisdiction, status)
   VALUES (uuid_generate_v4(), '<email>', NOW(), NOW(), 'GDPR'|'CCPA', 'pending_verification');
   ```
2. Perform identity verification. Send verification email to the address on file:
   - Include a unique verification link (e.g., `/dsar/verify/<token>`)
   - Require them to confirm within 7 days
   - Do not proceed with data compilation until verified
3. Once verified, update the row:
   ```sql
   UPDATE dsar_requests SET status='verified', verified_at=NOW() WHERE id='<dsar_id>';
   ```

---

## Fix
1. **Identify the user/org** — Query across all tables where the email appears:
   ```sql
   SELECT DISTINCT table_name FROM information_schema.columns
   WHERE column_name='email' OR column_name='user_email';
   ```
2. **Fan out data from multiple tables** — Extract:
   - `users` (account info, email, phone, created_at)
   - `organizations` (org names, roles, plan info)
   - `leads` (prospect data if generated by this org)
   - `properties` (property records)
   - `notes` (internal notes, communications)
   - `email_events` (email log)
   - `audit_events` (activity log, filtered by user/org_id)
   - Any other sensitive tables (transactions, documents, etc.)
3. **Produce JSON export**:
   ```bash
   npm run script -- dsar:export --email '<email>' --output /tmp/dsar_export.json
   ```
   This script should:
   - Query all relevant tables
   - Exclude rows from other users/orgs (privacy)
   - Redact sensitive fields (API keys, hashed passwords, internal IDs where possible)
   - Produce a machine-readable JSON file
4. **Compress and secure** — Encrypt the JSON file and send via secure channel (email with password, or secure file link with 7-day expiration).
5. **Log the fulfilment**:
   ```sql
   UPDATE dsar_requests
   SET status='fulfilled', fulfilled_at=NOW(), export_hash=MD5(<file>), export_method='encrypted_email'
   WHERE id='<dsar_id>';
   ```

---

## Verify
- Requester confirms receipt of data export and indicates completeness.
- Export file contains all requested tables with no data from other users.
- `dsar_requests` row shows `status='fulfilled'`, `fulfilled_at` timestamp is within the SLA window (30 days GDPR, 45 days CCPA).
- Audit log shows who fulfilled the request and when.

---

## Escalate if
- Requester cannot verify identity (email address not found in any system) — respond within SLA with "we have no record of this email address" (compliant response).
- Requester disputes that we hold data but you find it → consult legal@. May require deeper analysis (e.g., third-party data broker search).
- Request includes right to deletion (GDPR Art. 17) — escalate to legal@. Deletion is distinct from DSAR and has exceptions (legal holds, legitimate interests). Do not delete without legal approval.
- SLA deadline approaching (<7 days remaining) and request unresolved — escalate to legal@ immediately.

---

## Rollback
If you sent an export that later needs redaction:
1. Immediately notify the requester: "We sent you incomplete data. We are sending a corrected export."
2. Request they delete the first export.
3. Compile a new export with corrections and resend.
4. Update `dsar_requests` row with note on correction:
   ```sql
   UPDATE dsar_requests SET notes='First export sent, correction sent <date>' WHERE id='<dsar_id>';
   ```
