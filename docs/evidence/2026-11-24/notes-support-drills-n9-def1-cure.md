## The cure (N9-DEF-1)

Two READ-ONLY tools added to the support catalog (`server/ai/supportAgent.ts`),
registered at every registration point the codebase requires, and added to
the resolver's subset (`RESOLVER_TOOL_NAMES` in
`server/ai/paxSupportResolver.ts`, pinned from source in the drill tests —
an export with no production consumer would fail the reachability ratchet):

- `get_notes_book` — the two-book notes read: the SAME read the chat path's
  `get_notes` performs (serviced book via `storage.getNotes`, acquired book
  via `listAcquiredNotesForPax`, borrower contact resolved through the linked
  lead, and `buildNotesCoverageStatement` carried verbatim). It carries a
  support-only name because the tool registries (`shared/pax-controls.ts`
  TOOL_REGISTRY, `shared/pax-capabilities.ts` CAPABILITY_ROWS) key one
  dispatch per tool name and the chat name already belongs to `executeTool`.
- `get_note_delinquency_ladder` — the ladder read for one acquired note:
  `buildLadderView` from `server/services/notes/delinquencyLadder.ts`, the
  same service the delinquency route serves (current stage derived live from
  the next payment date, recorded stages, and the plain reason when there is
  no stage). A note id outside the org's acquired book returns the standard
  plain-words refusal.

Fences kept: both tools are in `PAUSE_SAFE_SUPPORT_TOOLS` (read-only — no
scope gate, no receipt hook, exactly like every other support read); the
resolver subset is pinned as exactly the prior 13 tools plus these two reads
— **no write, send, or borrower-contact power was added**; FD5 is untouched
and the resolver prompt now states the reads change nothing and no borrower
contact may be promised. Registration mirrors the support rows exactly:
`shared/pax-controls.ts` looks-and-drafts list, `shared/pax-capabilities.ts`
rows (family `note_investor`, coverage `two_book` / `single_slice` with
not-covered lines), and `docs/compliance/pax-capability-inventory.md`
regenerated by `scripts/pax-capability-inventory.mjs` (149 rows).
