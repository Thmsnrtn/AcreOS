# Email deliverability baseline — methodology + Tom action list

_Phase D3, paired with Beatrice's pre-deploy audit
(`docs/internal/beatrice-pre-deploy-review-2026-06-03.md`)._

This doc is the **methodology + interpretation guide** for the email
deliverability surface. The dated audit reports
(`email-deliverability-report-<YYYY-MM-DD>.md`) are generated by
`scripts/audit-email-deliverability.mjs`. This file does not snapshot
current state — it defines what the script measures and how to read it.

---

## Why this matters at Phase 0

A wave of acquisitions is incoming. AcreOS sends from a cold domain. The
realistic baseline expectation:

- 5–10% of welcome emails on a cold-sending domain land in spam regardless
  of how good the content is — purely because Gmail and Outlook have no
  reputation history for the sender yet.
- That rate compounds: spam-bucket landings mean lower open rates, which
  feed back into the reputation algorithm and make the next cohort worse.
- A clean DNS posture (SPF + DKIM + DMARC + MX) is a **necessary but not
  sufficient** condition. Reputation is also built by:
  - Sending only to engaged recipients during warming.
  - Honoring unsubscribes immediately.
  - Maintaining < 0.1% complaint rate (the SES throttling threshold).
  - Not sending to invalid addresses (bounce rate < 5%).

We catch the DNS half with this tooling and pair it with the existing
in-app surface (`server/services/emailService.ts` + `emailWarmup.ts` +
`emailSuppressions.ts` + `unsubscribeTokens.ts`).

---

## What the audit script checks

`scripts/audit-email-deliverability.mjs` runs five checks against a domain:

1. **SPF** — TXT record at the apex matching `v=spf1 ...`. Verifies a single
   record exists (RFC 7208 §3.2 forbids multiple), parses the
   include-mechanisms, classifies the all-mechanism (`~all` soft fail,
   `-all` hard fail).
2. **DKIM** — TXT records at `<selector>._domainkey.<domain>`. Defaults to
   the AWS SES rotation pattern (`0._domainkey`, `1._domainkey`,
   `2._domainkey`).
3. **DMARC** — TXT at `_dmarc.<domain>` matching `v=DMARC1 ...`. Parses
   policy (`none` / `quarantine` / `reject`), the percent, and the rua/ruf
   reporting addresses.
4. **MX** — confirms the apex has MX records.
5. **Welcome-email content** — reads the welcome template literal out of
   `server/services/emailService.ts` (`buildWelcomeTemplate`) and scores
   the link count, image-to-text ratio, spam-trigger words, and CAN-SPAM
   compliance (unsubscribe link + physical mailing address).

Output: `docs/internal/email-deliverability-report-<YYYY-MM-DD>.md`.

Severity rollup (exit codes):

| Severity        | Code | Meaning                                                                                   |
|-----------------|------|-------------------------------------------------------------------------------------------|
| `critical`      | 2    | SPF missing/malformed, or all DKIM selectors missing, or DMARC reject pre-warming.        |
| `warning`       | 1    | Partial DKIM, MX issues, DMARC malformed.                                                 |
| `informational` | 0    | DMARC monitor-mode (`p=none`) or missing — normal at Phase 0, but action queued.          |
| `clean`         | 0    | All four DNS checks pass with strong policy + content checks clean.                       |

## Tom's authoritative DNS action list

These are the records that must exist at the registrar (Cloudflare DNS for
`acreos.io`) for the platform to send mail with a clean posture. The
audit script reports which ones are missing.

### SPF

Single TXT at apex (`acreos.io`):

```
v=spf1 include:amazonses.com ~all
```

- `include:amazonses.com` authorizes AWS SES sending IPs.
- `~all` is the recommended soft-fail; flip to `-all` only after a month of
  clean DMARC aggregate reports.
- **Do not** publish a second SPF record. Receivers treat the multiple-SPF
  case as `permerror` and reject the whole evaluation. If a calendar
  provider needs to be added, **extend the existing record** with another
  `include:` mechanism — never add a separate record.

### DKIM

AWS SES publishes 3 CNAMEs (not TXT) for the rotation keys. After
verifying the domain in the SES console, add the three CNAMEs the console
hands you. They follow this shape:

```
<token1>._domainkey.acreos.io  CNAME  <token1>.dkim.amazonses.com
<token2>._domainkey.acreos.io  CNAME  <token2>.dkim.amazonses.com
<token3>._domainkey.acreos.io  CNAME  <token3>.dkim.amazonses.com
```

The audit script resolves them as TXT (CNAMEs follow through to the
underlying TXT) and checks each has a `p=` field. If you see two of three
selectors valid, SES has rotated and one CNAME is stale — re-verify in the
console.

### DMARC

Start in **monitor-mode** (Phase 0):

```
_dmarc.acreos.io  TXT  "v=DMARC1; p=none; rua=mailto:dmarc-rua@acreos.io; pct=100; adkim=s; aspf=s"
```

After 30 days of clean aggregate reports (defined as < 1% of mail failing
both SPF and DKIM alignment), upgrade:

```
_dmarc.acreos.io  TXT  "v=DMARC1; p=quarantine; pct=10; rua=mailto:dmarc-rua@acreos.io; adkim=s; aspf=s"
```

Ramp the `pct=` from 10 → 25 → 50 → 100 over the next 30 days, then upgrade
to `p=reject`.

### PTR / reverse DNS

If sending through SES, **Amazon owns the sending IPs and publishes the
PTR records** for them. No registrar action required. If we ever move off
SES, the new sending IPs must have PTR records that resolve back to a
hostname in `acreos.io` — receivers reject mail from IPs with mismatched or
generic PTRs.

## Warming schedule (cold-domain Phase 0)

Enforce server-side in `server/services/emailWarmup.ts` via
`reserveSend(orgId)`. The per-org daily cap is the throttle.

| Week | Daily cap | Audience                                                       |
|------|-----------|----------------------------------------------------------------|
| 1    | 10        | Founders + manually-invited beta only.                         |
| 2    | 30        | Engaged users (opened welcome, completed onboarding).          |
| 3    | 100       | All recent signups with confirmed email.                       |
| 4+   | Open      | Subject to SES quota — currently 50,000/day per sandbox-exit. |

A **single complaint on Gmail at week 1 volumes can tank the warming arc**.
Suppress flagged addresses immediately (`emailSuppressions.ts` already
handles this on SES feedback loop).

## What good looks like — Tom's checklist

Run the script monthly during Phase 0, then quarterly once warming is
complete.

- [ ] SPF: single TXT, `~all` (or `-all` post-month-1), `include:amazonses.com` present.
- [ ] DKIM: 3/3 SES rotation selectors resolve and parse with a `p=` field.
- [ ] DMARC: present; policy `p=none` during warming month, then ramped.
- [ ] DMARC `rua=` published — aggregate reports landing in a mailbox we read.
- [ ] MX: at least one MX record published (inbound mail capable).
- [ ] Welcome-email body: ≤ 10 links, image-to-text ratio < 1, no spam-trigger words in subject, unsubscribe link present, physical address in footer.
- [ ] Google Postmaster Tools registered for `acreos.io` and reviewed weekly during warming.
- [ ] SES bounce rate < 5%, complaint rate < 0.1%.

## Interpreting the dated reports

Each report opens with a summary line per check (✅/⚠️/❌/ℹ️) and an overall
severity. The body breaks each check down with the raw record text and a
list of issues. The final section is the **Findings + Tom-action items**
checklist — items in that list correspond 1:1 to DNS changes or content
edits required to clear the next audit run.

Reports are dated and accumulate in `docs/internal/`. Do not delete old
reports — they are the historical record of the deliverability posture.
