## One-sentence thesis

We have safety *mechanisms* (guard, eval set, grounding prompt, task router) but not yet a safety *system*: nothing measures Pax's actual hallucination rate on a live signal, the strongest gate we built (`gateOutputOrThrow`) is not on the live customer path, our eval is still substring contains-checking, and the classifier that decides whether to downgrade a customer-facing turn to Haiku has never been measured for misroute rate. Elevation = make Pax's trustworthiness a *measured, defended, self-correcting* property, and make Pax sound like the sharpest land analyst in the room rather than a careful generic assistant.

## What I verified in the codebase (grounding for this plan)

- **The shipped substrate is real and good.** `server/ai/paxPromptVersions.ts` (DATA_GROUNDING dg-v1, versioned + changelogged + logged), `server/services/paxHallucinationGuard.ts` + `server/ai/paxSourceExtraction.ts` (guard now fed real source context from `toolCallsExecuted`), the block-and-retry-then-deflect loop in `server/ai/executive.ts:1789-1888`, `server/ai/dataGroundingEvalCases.ts` (18 cases with adversarial fixtures), `server/ai/paxModelTier.ts` (eval-gated task-type cost routing with a single reversible `DATA_GROUNDING_EVAL_GREEN` switch). Voyage client is production-grade (`server/services/embeddings/voyageClient.ts`). This is a strong foundation — I am building on it, not redoing it.
- **GAP A — the strongest gate is not on the live Pax path.** `gateOutputOrThrow` (`server/services/aiEvalHarness.ts:57`) is only called from `server/services/complianceAI.ts`. The live Pax executive loop relies on `guardPaxOutput` (numeric/entity heuristics) but never runs the customer turn against the *critical* `pax_inbox` test cases at runtime. Our best regression net is CI-only.
- **GAP B — eval is substring contains-check v0.** `evaluateTraits` / `gateOutputOrThrow` are case-insensitive `.includes()`. The harness header itself flags "Future iterations will add LLM-judge eval." Meanwhile a real LLM-judge stack already exists for the founder side (`server/services/scpLLMJudges.ts` — triple-Sonnet minority-veto, cascaded Haiku→Sonnet regression). Pax has none of it. A paraphrased hallucination ("it's a low-risk flood area" instead of the forbidden "minimal flood risk") slips the contains-check.
- **GAP C — no hallucination *rate*; no quality-drift audit.** `server/services/andrei/aiQualityAudit.ts` (the 7-detector loop in my charter) does not exist. There is no `andrei_audit_findings` table. We log warnings per turn but never roll them into "dg-v1 has a 0.4% flagged-hallucination rate on N production turns this week." We cannot defend a number we don't compute.
- **GAP D — the cost router's classifier has never been measured.** `classifyPaxTaskType` (`server/ai/paxModelTier.ts:237`) is a regex heuristic that can downgrade a customer-facing turn from Opus to Haiku. There is no eval of its misroute rate (a reasoning turn misread as `data_lookup_restate` gets Haiku silently), and no per-task-type eval proving Haiku actually passes dg-v1 for `data_lookup_restate` (the policy `rationale` *asserts* it but no test pins it).
- **GAP E — confidence is prose, not calibrated.** The grounding prompt tells Pax to hedge ("high/likely/uncertain"); nothing checks whether Pax's stated confidence tracks reality. There is no calibration/Brier measurement. A premium-honest assistant should be *calibrated*, not just hedged.
- **GAP F — no land-domain knowledge layer for Pax.** Pax grounds entirely on in-context tool results + a static persona prompt. The Voyage client + `vectorSearch`/`decisionLogRag` exist but Pax has no retrieval over a curated land-investing knowledge base (FEMA zone semantics, SSURGO class meanings, seller-finance/note mechanics, common diligence pitfalls). Pax is accurate on *retrieved parcel facts* but generic on *land expertise*.

## Top elevation ideas (priority order)

### 1. Put the eval gate on the live Pax path — runtime critical-case gating
- **refine → improve · customer · effort S**
- **Why / what "great" looks like:** We built `gateOutputOrThrow` and a set of *critical*-severity `pax_inbox` cases precisely to stop the worst outputs, then wired only the weaker heuristic guard to the live loop. Great = every customer turn that trips a critical forbidden-trait (e.g. naming a flood zone after a miss) is caught at runtime by the same assertions our CI uses — defense in depth, not CI-only. The guard catches *fabricated numbers/entities*; the eval gate catches *forbidden semantic patterns* the guard can't see.
- **First step:** In `server/ai/executive.ts`, after the `guardPaxOutput` block (~line 1885) and before `createMessage`, call a lightweight in-process variant of `gateOutputOrThrow` against `surface="pax_inbox"` critical cases — but instead of throwing, fold failures into the existing correction/deflection path (reuse the `correctionInstruction` machinery). Keep it off the streaming hot loop by running it on the assembled `fullResponse`. Add a kill switch mirroring `DATA_GROUNDING_EVAL_GREEN`.

### 2. LLM-judge eval layer for Pax (semantic, not substring)
- **improve · both · effort M**
- **Why / what "great" looks like:** Contains-checking is a 2026-05 stopgap; a paraphrased hallucination passes it. We already run a rigorous judge stack on the founder evolution engine (`scpLLMJudges.ts`: triple-Sonnet minority-veto for safety, Haiku→Sonnet cascade for regression). Great = Pax's data-grounding eval is judged *semantically* by a cheap cascaded judge (Haiku screens, Sonnet adjudicates disagreements), so "low-risk flood area" is caught even though the literal forbidden string isn't present. The number becomes trustworthy enough to make model-swap decisions on.
- **First step:** Add a `groundingJudge` to `aiEvalHarness.ts` modeled on `scpLLMJudges` regression cascade: judge prompt = "Does this answer assert any parcel fact (flood/soil/acreage/zoning/owner) not present in the provided source context? Does it cite source+vintage for facts it does state? Answer PASS/FAIL + reason." Run it as a second scorer alongside contains-check; disagreements between the two become new hand-labeled cases. Cost-gate it (judge only on the dg cases, not every prod turn).

### 3. `aiQualityAudit.ts` — the 7-detector quality-drift loop (from my charter)
- **develop · founder · effort M**
- **Why / what "great" looks like:** My charter specifies a continuous-audit loop at `server/services/andrei/aiQualityAudit.ts` complementing Beatrice's constitutional-drift audit. It does not exist. Great = before a customer ever notices Pax getting worse, a detector fires to Solene: eval-pass-rate regression >2pp w/w, hallucination-flag-rate spike >50% over rolling baseline, cost-per-interaction creep >10% m/m, latency p95 >8s, model-upgrade action overdue, prompt-edit-without-eval-coverage, embedding-recall drift. Quality becomes self-monitoring.
- **First step:** Create `server/services/andrei/aiQualityAudit.ts` + an `andrei_audit_findings` table (migration). Implement detector #2 first (hallucination-flag-rate spike) — it reads the `__hallucinationWarnings` already persisted on assistant messages (`executive.ts:1897`) and the `[pax] hallucination warnings` log signal; compute a 7-day rolling baseline and fire on a >50% deviation. Wire to a daily scheduled job in `runScheduledJobs.ts`. Add detectors incrementally.

### 4. Measure + defend the cost router's classifier (misroute rate as a tracked metric)
- **refine · both · effort S–M**
- **Why / what "great" looks like:** `classifyPaxTaskType` can route a customer turn down to Haiku. That's the right idea (data-restatement is cheap-model work) but it's currently faith-based: no test proves Haiku passes dg-v1 for `data_lookup_restate`, and no eval measures how often a reasoning turn is misclassified as a lookup (the dangerous downgrade). Great = a labeled classifier eval set + a per-task-type model eval, so each policy `floorModel` is backed by a green number, and misroute rate is a tracked metric with a regression alarm. This is the literal precondition my own lens (item 7) wrote: "cannot route customer-facing synthesis below the safety bar without an eval supporting it" — make that eval real, per task type.
- **First step:** Build a ~40-case labeled classifier set (text → expected `PaxTaskType`) in a `paxTaskClassifier.eval.ts`; assert misroute rate < threshold. Then run dg-v1 against Haiku and Sonnet specifically for `data_lookup_restate`/`data_summary`/`formatting` and record per-model pass rate in the policy `rationale` (replace the prose assertion with a cited number). Add a "downgraded turn that later tripped the guard" counter to detector #4 in audit (item 3).

### 5. Pax land-expertise retrieval layer (curated KB, not parcel facts)
- **elevate · customer · effort M–L**
- **Why / what "great" looks like:** Pax is rigorous on *retrieved parcel facts* but generic on *land domain knowledge* — what FEMA Zone AE actually constrains, what SSURGO class IIe means for septic/perc, how seller-finance note structures and usury caps work, the classic diligence traps (landlocked/no legal access, back-taxes, easement-only access, mineral-rights severance). The Voyage client + pgvector + `decisionLogRag` are already built and idle pre-Phase-2. Great = a small, hand-curated, *cited* land-knowledge corpus retrieved into the prompt so Pax sounds like a 20-year land investor, with every explanatory claim still attributable. This is the distinctiveness lever — it's what makes the free tier feel like an expert, not a chatbot.
- **First step:** Author ~50–100 short, sourced land-knowledge cards (markdown w/ citations). Embed via the existing Voyage client; store in pgvector (`embeddings/pgvectorInit.ts`). Add a `retrieve_land_knowledge` tool to `server/ai/tools.ts` that Pax calls for explanatory ("what does Zone AE mean for building?") turns, distinct from parcel-fact lookups. Extend DATA_GROUNDING: knowledge-card claims must cite the card; never blend a card's general statement into a parcel-specific assertion. Gate behind a feature flag; eval the retrieval recall before it touches a customer.

### 6. Confidence calibration — make Pax's hedges *earned*
- **elevate · customer · effort M**
- **Why / what "great" looks like:** "Premium-honest" means calibrated, not just hedged. Right now Pax says "high/likely/uncertain" with no feedback loop proving those words mean anything. Great = we map provider `confidence` + cache staleness to discrete bands, and over time measure whether "high" claims are actually right more often than "uncertain" ones (Brier-style on a labeled subset). When a county layer is 14 months stale, the band drops automatically — turning a data weakness into a trust signal, defensibly.
- **First step:** Add a structured `confidenceBand` (high/moderate/low) derived deterministically from broker `confidence` + `cachedAt` age, surfaced both in the provenance envelope and as the phrase Pax must use. Log (band, was-later-corrected) pairs. Add a calibration detector to `aiQualityAudit` once enough labeled turns accrue.

### 7. Prompt-versioning discipline as enforced infrastructure (not convention)
- **refine · founder · effort S**
- **Why / what "great" looks like:** DATA_GROUNDING is beautifully versioned (`DATA_GROUNDING_VERSION` + changelog + "no merge without an eval number"). But that discipline lives in a comment and a code-review norm, not a check. The response-shape prompt (`PAX_RESPONSE_SHAPE_V3`) has no version constant, no changelog, no eval delta. Great = every customer-facing system prompt has a version + changelog + a covering eval case, and a CI check fails a PR that edits a versioned prompt without bumping the version or touching the eval set (charter detector #6: "prompt-without-eval-coverage").
- **First step:** Add `PAX_RESPONSE_SHAPE_VERSION` + changelog to `paxPromptVersions.ts` mirroring DATA_GROUNDING. Write a `tests/unit/promptVersionDiscipline.test.ts` that snapshots prompt-string hashes and fails if a hash changes without a version bump. This is the cheapest way to make eval-first a *property* of the repo rather than a habit.

## My single BOLDEST elevation bet

**Make Pax the only land-investing assistant with a published, continuously-measured hallucination rate — and put that number in the product.** Combine items 1+2+3+6: live eval gating, semantic judge eval, the quality-drift audit, and calibration into one loop that produces a single trustworthy metric ("Pax's data-grounding accuracy on N turns this week: 99.6%, calibrated"). Then surface a tasteful version of it to customers — a "how Pax handles data" page that says, honestly, "Pax cites a source for every parcel fact and refuses to guess; here's our measured accuracy and how we test it." Every competitor's AI says "may produce inaccurate information" in 8pt gray. We'd be the one that *measures it, defends it, and shows the work.* For a product where a wrong flood-zone call is a liability event, verifiable trustworthiness isn't a feature — it's the entire moat. Bold because it requires holding ourselves to a number publicly; that's exactly why it's distinctive.

## Small, high-ROI polish refinements

- **Pin per-model pass rates in the routing policy `rationale`** (`paxModelTier.ts`) — replace "Haiku passes the dg-v1 eval" prose with the actual measured number + date.
- **Stop hardcoding cost rates in two places** — `executive.ts:1908` has a `COST_PER_MILLION_TOKENS` map that omits the Anthropic models the router actually uses (Opus/Sonnet/Haiku), so the per-turn cost estimate for the primary models silently falls back to the `{1, 3}` default. Source it from `server/services/aiCostRates.ts`.
- **`logDataGroundingVersion` logs once per process** — good, but it's the only prompt module that does. Emit the active version of *every* versioned prompt on boot for auditability.
- **Add the missing `adversarialOutput` fixtures** — several dg cases (e.g. `dg-hit-flood-001`, `dg-hit-soil-001`, `dg-hit-zoning-001`, `dg-hit-owner-001`) have no `adversarialOutput`, so the guard isn't unit-tested against a hallucinating answer for those scenarios. Cheap to add; tightens the net.
- **Tune `paxSourceExtraction` non-fact key list** — `"id"` as a substring match also strips legitimate fact keys like `"avgGridSize"`→no, but `"valid"`, `"residential_units"` could be caught; audit `NON_FACT_KEY_SUBSTRINGS` against real enrichment payloads to avoid over-stripping source numbers.
- **Classifier precedence edge case** — "what's the *best* flood zone" or "*rank* these by acreage" hits both MULTI_PARCEL and DATA_LOOKUP; precedence (reasoning wins) is correct but untested for the overlap; add 3–4 overlap cases.
- **Emit the routed `taskType` + model on the `done` SSE event** so the client (and Krieger's surface) can show which model answered — useful for the cost-transparency story and for debugging a bad downgrade.

## The one thing that would most embarrass us if a sharp first customer (or I) noticed it unpolished

**A paraphrased hallucination that our substring eval and our guard both miss — on the customer's first real deal.** Our entire trust story rests on "Pax cites sources and won't guess," but the runtime defenses are (a) a numeric/entity heuristic guard and (b) a *contains-check* eval that lives only in CI, not on the live path. A customer asks "is this lot OK to build on?" after a zoning *miss*; Pax says "this looks like a buildable agricultural-type parcel" — no forbidden literal string, no fabricated number, so the guard stays quiet and the CI-only eval never runs on this turn. That's a confident wrong implication that sails straight through, and it's exactly the failure mode we told ourselves we'd closed. Items 1 (live gate) and 2 (semantic judge) exist specifically to close it, and until they ship, "Pax won't guess" is a claim we can't fully defend on the live path.
