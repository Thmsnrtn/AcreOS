## Red Team Fix Verification (DEFECT-0069 through DEFECT-0072)

### DEFECT-0071: Deal Room Org Scoping -- PASS

**File:** `server/routes-deal-rooms.ts`

The `getDealRoomOrFail()` helper (lines 45-63) correctly:
- Extracts `organizationId` from request via `getOrganizationId(req)`
- Fetches the deal room by ID
- Verifies the requesting org is a participant: `participants.some(p => p.organizationId === organizationId)`
- Returns `Errors.notFound()` (not 403) if the org is not a participant, preventing enumeration

All 11 route handlers call `getDealRoomOrFail()` before accessing any deal room data. No regressions detected.

### DEFECT-0070: Billing Permissions -- PASS

**File:** `server/routes-billing.ts`

Every billing endpoint uses `requirePermission("canManageBilling")` middleware (17 instances confirmed). The permission is role-gated in `server/utils/permissions.ts` -- only `owner` and `admin` roles have `canManageBilling: true`. No billing route is accessible to `member` or `viewer` roles.

### DEFECT-0069: GDPR Export No Truncation -- PASS (with observation)

**File:** `server/services/gdprService.ts`

The export function uses `MAX_EXPORT_RECORDS = 100_000` as a safety cap on each query. It also fetches `totalRecords` counts via separate `count()` queries so the response reveals whether truncation occurred. This is the correct GDPR-compliant approach -- the export includes actual record counts alongside the exported data, allowing the user to detect if the cap was hit.

**Observation (P2):** If a user has >100,000 leads, they receive 100,000 rows but the totalRecords.leads shows the real count. The export does not paginate or stream. For very large accounts, this could OOM. Current cap is reasonable for launch.

### DEFECT-0072: Browser Job Org Scoping -- PASS

**File:** `server/routes-misc.ts`

- `GET /api/browser-automation/jobs` (line 139): Calls `getOrganizationJobs(org.id, ...)` -- org-scoped
- `GET /api/browser-automation/jobs/:id` (line 154): Fetches job, then checks `job.organizationId !== org.id` and returns `Errors.notFound()` if mismatch
- `POST /api/browser-automation/jobs/:id/cancel` (line 191): Same org-scoping check before allowing cancel

All browser automation endpoints are properly org-scoped.

## Edge Cases (Lenses 101-110) -- 2 issues found

### Checked:
- `server/routes-deal-rooms.ts` -- error handling, input validation
- `server/routes-misc.ts` -- zero-state handling
- `server/services/gdprService.ts` -- extreme-length input handling

### Findings:

**ISSUE-S1-01 (P1): `parseInt()` without NaN guard in deal room routes**
`server/routes-deal-rooms.ts` uses `parseInt(req.params.id)` (lines 86, 98, 124, etc.) without checking for `NaN`. If a non-numeric `:id` is passed, `parseInt` returns `NaN`, which is passed to the DB query. Drizzle may handle this gracefully, but the lack of explicit validation means an attacker can probe error responses for information leakage. The same pattern exists in 11 route handlers.

**ISSUE-S1-02 (P1): Raw `res.status().json()` instead of `Errors.*` helpers in deal room routes**
`server/routes-deal-rooms.ts` has 14 instances of raw `res.status(N).json({ error: ... })` in catch blocks and validation responses (lines 154, 189, 213, 220, 225, 268, 311, 331, 375, 404, 437, 491, 566, 617). Per CLAUDE.md, all error responses must use `Errors.*` helpers to maintain the standardized `{ error, message, details?, statusCode }` shape. This inconsistency could confuse frontend error handling.

## Security Depth (Lenses 111-120) -- 1 issue found

### Checked:
- `server/middleware/csrf.ts` -- CSRF double-submit cookie implementation
- `server/middleware/secretsValidation.ts` -- hardcoded secret detection
- `server/services/browserAutomation.ts` -- DNS SSRF protection
- `server/routes-deal-rooms.ts` -- document signing secret

### Findings:

**CSRF protection: PASS**
Double-submit cookie CSRF is active on all `/api` routes via `server/routes.ts:625`. Safe methods (GET/HEAD/OPTIONS) are exempt. Webhook paths starting with `/webhook` are exempt. Bearer-token API clients are exempt. Implementation is correct.

**DNS SSRF check in browser automation: PASS**
`server/services/browserAutomation.ts` lines 12-30 define DNS resolution helpers. Lines 818-847 resolve hostnames via DNS, check both IPv4 and IPv6 against private IP ranges, and block internal addresses. SSRF protection is re-enabled and functional.

**Hardcoded secrets throw in production: PASS**
Three patterns confirmed:
- `server/routes-deal-rooms.ts:299-301`: `DOCUMENT_SIGNING_SECRET` throws in production, uses `dev-fallback-not-for-production` in dev
- `server/jobs/courseCompletionCheck.ts:41`: Same pattern for `CERT_SECRET`
- `server/services/configManager.ts:27-31`: Same pattern for encryption key fallback
- `server/middleware/secretsValidation.ts:116`: Calls `process.exit(1)` in production if required secrets missing

**Multi-tenant isolation: PASS**
Deal rooms use `getDealRoomOrFail()` with org-scoped participant check. Browser automation uses explicit `org.id` comparison. Billing routes use `org.id` from authenticated request.

**ISSUE-S1-03 (P1): CSRF exempt prefix `/webhook` also exempts `/api/webhooks` PUT endpoint**
The CSRF exempt prefix list includes `/webhook` (line 8). When the CSRF middleware is mounted at `/api`, a request to `/api/webhooks` (PUT, for saving webhook configs) has `req.path` = `/webhooks`. Since `/webhooks`.startsWith(`/webhook`) is true, the PUT endpoint bypasses CSRF protection. This endpoint is authenticated and admin-gated (`requireAdminOrAbove`), but a CSRF attack against an admin's browser session could modify webhook endpoints. The fix is to make the prefix more specific: `/webhooks/twilio`, `/webhooks/inbound-email`, `/webhooks/dropbox-sign`, `/webhooks/meta-lead-ads`, `/webhooks/actum` -- or use `/webhook/` (with trailing slash) since the external callbacks all have sub-paths.

## Launch Readiness (Lenses 141-150) -- 2 issues found

### Checked:
- `.github/workflows/ci.yml` -- CI pipeline
- `Dockerfile` -- deterministic build
- `.nvmrc` + `package.json` -- Node version alignment
- `package.json` -- pre-commit hooks

### Findings:

**CI pipeline: PASS**
`.github/workflows/ci.yml` runs: TypeScript check, ESLint, test coverage, build, Playwright E2E, CodeQL security scan, and Docker image build. All steps use `node-version: 22` consistently.

**Dockerfile deterministic: PASS**
- Uses pinned Node version: `ARG NODE_VERSION=22.21.1` (not `latest`)
- Uses `npm ci` (not `npm install`) for deterministic installs
- Multi-stage build with production prune
- Non-root user (`USER node`) for container security

**Node version alignment: PASS**
- `.nvmrc`: `22`
- `package.json engines`: `"node": ">=22"`
- `Dockerfile`: `22.21.1`
- CI workflows: `node-version: 22`
All aligned on Node 22.

**ISSUE-S1-04 (P2): No pre-commit hook for staged TypeScript checking**
`package.json` has no `husky`, `lint-staged`, or `pre-commit` configuration. No `.husky/` directory exists. Developers can commit TypeScript errors directly to the repository. The CI pipeline catches them, but a pre-commit hook would provide faster feedback and prevent broken commits from reaching the remote.

**ISSUE-S1-05 (P2): Job queue `/api/jobs/:id` lacks org scoping**
`server/routes-misc.ts` line 488: The `GET /api/jobs/:id` endpoint fetches a job by ID and returns it to any authenticated user. The `Job` interface in `server/services/jobQueue.ts` does not have an `organizationId` field (only the payload may optionally contain one). Any authenticated user can read any job's status and payload by guessing/enumerating UUIDs. Unlike browser automation jobs, which have explicit org checks, the generic job queue has no tenant isolation on the read path.
