## Lens 051 -- Concurrency / Race Conditions

### Webhook idempotency (DEFECT-0006)

**Status: PASS -- no regression**

`server/webhookHandlers.ts:32-45` -- `claimEvent()` uses atomic `INSERT ... ON CONFLICT DO NOTHING ... RETURNING` on the `stripeProcessedEvents` table. If no row is returned, the event was already claimed. This eliminates the original TOCTOU race between `isDuplicate()` and `markProcessed()`.

Evidence:
- `db.insert(stripeProcessedEvents).values({...}).onConflictDoNothing().returning()` (line 34-37)
- `processWebhook()` calls `claimEvent()` before dispatch (line 63-66)
- Duplicate events are logged and skipped without processing

### Credit allowance unique constraint (DEFECT-0007)

**Status: PASS -- no regression**

`migrations/0025_credit_allowance_month_unique.sql` creates:
- Column `allowance_month` on `credit_transactions`
- Unique index `credit_txn_allowance_month_org_uniq` on `(organization_id, allowance_month)`

`server/services/credits.ts:248-291` (CreditService.applyMonthlyAllowance) and lines 496-539 (UsageMeteringService.applyMonthlyAllowance) both:
- Use `withTransaction()` to wrap balance update + transaction insert
- Use `.onConflictDoNothing().returning()` on the credit transaction insert
- If the insert returns 0 rows (conflict), reverse the balance update within the same transaction

### Campaign send upfront deduction

**Status: PASS -- no regression**

`server/routes-campaigns.ts`:
- Email send (line 1617-1629): `DEFECT-0047` comment confirms upfront atomic deduction via `creditService.deductCredits()` before any emails are sent
- SMS send (line 1755-1766): Same pattern -- deduct before send
- Direct mail (line 688-699): Credits deducted before mail pieces dispatched

`deductCredits()` itself (`credits.ts:96-107`) uses an atomic `UPDATE ... SET balance = balance - X WHERE balance >= X` pattern, so check-and-deduct is a single SQL statement -- no TOCTOU.

### NEW FINDING: deductCredits ledger desync risk (P2)

`credits.ts:96-123` -- `deductCredits()` performs the balance UPDATE (line 96-107) and the transaction log INSERT (line 113-123) as **separate SQL statements without a wrapping transaction**. If the process crashes between the UPDATE and the INSERT, the balance is deducted but no transaction record exists. Contrast with `addCredits()` (line 46-73) which correctly wraps both in `withTransaction()`. This was fixed for adds (P0 DI-001) but not for deducts.

**Severity: P2** -- The balance deduction is still atomic for race prevention. The risk is only ledger desync on crash, not double-spending.
