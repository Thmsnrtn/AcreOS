# AcreOS: from profile selection to a business that actually works

**Read-only product, technical and operating review — September 29, 2026**  
**Pinned source:** `Thmsnrtn/AcreOS`, `claude/acreos-canonical-implementation-1asgvc` at `a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31`. Branch ref was checked for this review. **No repository edits, test execution, authenticated UI inspection, provider connection, or production verification.** This follows [the profile-complete journeys report](AcreOS_Profile_Complete_Journeys_2026-09-29.md), which supplies the job for all 15 business types and the three note roles.

## Executive assessment

AcreOS has an unusually broad set of working parts: a five-door customer shell, extensive domain routes, tailored copy and synthetic fixtures, data provider orchestration, CRM/outreach, rental and note engines, founder controls and AI surfaces. The quality question is now **whether a specific investor can enter with their real starting state, make a consequential decision using honest evidence, carry it through an external and internal workflow, and know what happened afterward**. Source reachability is a weaker test. No amount of visual polish turns a misattributed mailbox, an invented fee, or synthetic onboarding progress into a dependable operating system.

I inventoried the active App route declaration (about 300 paths, including public, founder, aliases, gated and specialized routes), the customer/founder navigation, business-type registry and sample seeder, then selectively traced onboarding, inbox/mailbox, MCP, provider, finance, export and representative domain code. The matrix below covers every **customer-facing feature family exposed by that inventory**, plus platform/founder capabilities; it does not claim line-by-line verification of every route or real-world completion. Every row supplies a customer outcome and a falsifiable quality test. Internal tests, comments and badges are evidence of implementation intent, not live qualification.

It measures first interaction/progress, not necessarily a customer outcome; synthetic data must be explicitly excluded or separately marked. Keep the useful speed metric, name it accurately, and add a later task-completion measure by profile.

A second user or same-provider account is a concrete identity-binding risk; it must be reproduced under a controlled double before calling it an exploit.

It offers a second, on-demand Gmail/Outlook experience rather than a clear unified communication model. Gmail list makes up to 25 metadata fetches in parallel with no explicit timeout ([client](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/mailbox/mailboxClient.ts#L257-L328)). This is a likely scale/latency risk, not an observed timeout.
- The mailbox [settings dialog](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/client/src/components/native-mail-panel.tsx#L84-L169) reads `mailbox.settings`, but [GET `/api/mailbox`](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/routes-mailbox.ts#L130-L150) does not select settings; it also exposes “connected” without a proven provider read or scope check. Signature and reply tone are stored by PATCH but are not applied by the native send or summary path inspected. The displayed setting can therefore differ from effective behavior.
- The [reply](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/client/src/components/native-mail-panel.tsx#L222-L250) passes an API message ID as `In-Reply-To`, and the provider clients put it in an email header ([Gmail/Graph](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/mailbox/mailboxClient.ts#L342-L440)). A provider's opaque ID is not necessarily the RFC Message-ID header. Test threading against real messages. The Graph `sendMail` response is `202 Accepted`, which Microsoft explicitly says does **not** prove processing completed; the UI currently says “Reply sent” [Microsoft Graph](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0).
- The [summary service](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/mailbox/threadSummary.ts) sends an opened message's subject/body (capped) to the AI router automatically and caches the summary in process keyed only by message ID. It neither scopes the cache by org/mailbox nor makes this processing choice visible at the reading moment. “No copy kept here” refers to local persistence; it is not a complete account of model processing. Untrusted email is also prompt-injection material. Preserve the useful summary, but qualify processing and scope, opt-out, data rights, and behavior under an adversarial message.
- The shared [Finance summary](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/routes-finance.ts#L997-L1055) can mislabel closed accepted amounts as collected assignment fees and list-price spreads as project P&L. ## Onboarding as experience-shaping, not a three-screen form

The current wizard has a genuine improvement worth preserving: three steps after an AI disclosure, 15 choices via progressive disclosure, note-role selection, per-type copy and destinations, skip/rerun, a single sample seeder, real checklist signals and a founder funnel. It is [explicitly structured](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/client/src/pages/onboarding-v2.tsx#L1-L39) for speed and mobile. The secondary types are actually reachable behind “Show all investor types,” not only later in Settings ([choices](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/client/src/pages/onboarding-v2.tsx#L110-L171)); an introductory comment saying otherwise is stale. Do not replace this with a long survey.

The mature flow has **two entry modes** and a resumable first task:

| Moment | What the investor should experience | Current anchor / decisive improvement |
|---|---|---|
| Identity and consent | Know the workspace and individual identity, what AI processes, and what external access is optional. | AI disclosure gate exists; preserve it. Clarify separately when mailbox content is sent to model providers. |
| Strategy | Choose one or several asset/business strategies, then a role where the work differs (note invest/originate/service, client agency vs own investment). | Fifteen types/three note roles exist. Keep the org's business model separate from a user's personal lens and a deal's actual type; do not let Settings silently change teammates' organization. |
| Starting state | “I'm exploring my first property” or “I already own/manage assets.” Ask the smallest extra question that picks the first job. | Current Step 1 asks name/type, not portfolio state. The universal CSV imports leads, so an operating portfolio is a detour. |
| First data | Offer a direct useful lookup, type-specific import, or clearly marked sample; preserve provenance. Never force a paid connector before a free first insight. | Single synthetic seeder is useful; the Map's [sample parcel preview](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/client/src/pages/maps.tsx#L1080-L1083) is a useful real-free-data example. Build type-specific import adapters only where actual demand/data exists. |
| Save and verify | Progress only when profile/data state is durably correct, or explain what failed with retry. | Replace `allSettled` success assumption and nonfatal mismatch in completion. Idempotently resume after reload; do not create duplicate templates or records. |
| Job invitation | One action meaningful to that user, with missing evidence clear. | The current finish destination varies by type, but checklist signals for four landlord types still center on seller acquisition. Provide an existing-book job and a zero-to-one job. |
| Autonomy and connections | State what the app can read, propose, send, charge, and observe; connect only what the selected job needs. | Optional “connect services” item exists. Qualify actual provider scopes and health before showing “connected”; no global autonomy toggle. |
| First business result | Prove a useful decision or operation, not a quick click. | Keep “time to first interaction” under 90s as a UX metric; measure first *qualified* result separately by profile and sample/live cohort. |
| Return visit | Resume the exact work, show changed data and obligations, acknowledge completion/error. | Today and Welcome Back exist; test the full timeline after 1 day, 1 week, interrupted setup, missing provider, and a real incoming message/payment. |
| Growth/change | Add another strategy/book without resetting the first, invite teammates with explicit authority, recover connection, export complete history. | Re-run preserves type/role by documented design; settings persona write and org reconciliation need a multi-user invariant. |

**Instrumentation:** Record `setup_started`, `profile_confirmed`, `data_source_selected`, `first_useful_result`, `first_decision`, `first_external_action_confirmed`, `first_obligation_handled`, and `returned_to_work` as **proposed events only if the existing lifecycle stream cannot express them**. Each needs origin `sample|manual|provider`, object type, business type, actor, authority, and timestamp. Never count a generated fixture as a customer's economic milestone. The founder funnel should report activation by profile, starting state and source availability; setup speed, conversion to first real job, time to that job, return after a week, and drop-off reasons are different quantities. Sample size and missing attribution must be visible.

## Native inbox and email: complete worked example

**Answer to the MCP question.** A user can see code for a native Gmail/Outlook **OAuth via Clerk** connection in Settings and a Mail tab that reads/sends on demand. It is not a mailbox connection “through MCP.” AcreOS also exposes itself as an MCP server for **external AI clients**. The current HTTP MCP [safe-intent filter](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/mcp/safeIntents.ts#L1-L30) intentionally excludes write/send actions. That is appropriate. A future MCP mail tool would sit *after* the same OAuth account binding, permission and audit checks, and should begin read-only. The repo also has a distinct legacy `/api/mcp/execute` and local stdio MCP implementation; [mounts](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/routes.ts#L1485-L1491) warrant consolidation review before exposing new capabilities. MCP's existence does not qualify the mail integration.

**What is implemented, from source:** Settings calls Clerk `createExternalAccount` for Gmail `gmail.readonly` and `gmail.send`, or Graph `Mail.Read` and `Mail.Send`; returns to record an org-scoped mailbox row; API lists and reads messages and sends via a fresh Clerk token without local message/token persistence; reply UI, per-mailbox settings, search, a one-line AI summary and an empty state exist. This is a serious starting point. [Clerk token API](https://clerk.com/docs/reference/backend/user/get-user-oauth-access-token) supports fetching provider OAuth tokens, but production configuration, granted scopes, Google verification, Microsoft consent, and live delivery remain **unverified**. Gmail `gmail.readonly` is a restricted scope with verification requirements [Google scopes](https://developers.google.com/workspace/gmail/api/auth/scopes). A read-only review cannot infer those were completed.

**The mature job:** An investor connects the correct business account with informed scope consent; sees which mailbox it is, who may view or send, last successful read and current limitations; processes a seller/buyer/tenant/borrower thread from one place; links it to the correct contact and deal with confidence, not fuzzy name guesswork; sees the next obligation, proposes a reply, edits and sends with explicit authority; sees *accepted by provider* versus *sent/delivered/failed* honestly; can search history, paginate, attach relevant evidence, and recover a broken connection. Mobile triage should be fast, with a clear reading/reply surface and undo/draft safety. The account owner can disconnect without silently deleting the deal's own audit and obligation records, subject to stated retention policy. Mature team sharing is an explicit delegation permission, not the mere fact that a mailbox row belongs to the same organization.

**Repair order and acceptance:**

1. **Identity boundary (P0):** A mailbox row must bind to a specific Clerk external account and granted scopes. For list/read/send, resolve the token *for that account*, or refuse if no such token exists; authorize viewer/sender according to row ownership/delegation. Test org A/B, Alice/Bob in one org, two Gmail accounts for Alice, a revoked Clerk connection, and same-provider account replacement. Assert the response never contains content from or sends through a different account. The current `getUserOauthAccessToken` first-token behavior cannot be assumed account-specific; Clerk's token object includes an external account ID and scopes [Clerk token type](https://clerk.com/docs/reference/backend/types/backend-oauth-access-token). If Clerk cannot vend a selected account safely under this integration, constrain the product to one account per provider per user and say so.
2. **Connection truth (P0/P1):** After callback, compare returned external account/email/scopes with requested account, perform a harmless live read, and show linked / needs consent / read works / send permitted / degraded / revoked with last checked time. GET settings must return saved settings; effective signature/tone behavior must be implemented or removed from UI. A redirect or inserted row is not provider qualification. Record nonsecret failures without token or message body.
3. **Send/reply truth (P0):** Use RFC Message-ID and provider-supported reply semantics; escape user text in HTML and provide text/plain where feasible. Preserve draft across failure. After Graph 202 say “Accepted by Microsoft; delivery unconfirmed,” and look for provider evidence where allowed; don't automatically retry an ambiguous send. Gmail response ID is evidence of provider acceptance, not recipient receipt. Test original sender/account, real Gmail and Graph threads, alias, unicode, attachment boundary, duplicate click and network timeout after provider acceptance. Microsoft’s own docs distinguish 202 acceptance from completion [Graph sendMail](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0).
4. **Complete reading and flow (P1):** Consume `nextPageToken` with bounded infinite pagination; show search scoped to the selected mailbox, unread/assigned/needs reply, contacts and deals, attachments and safe HTML/text, and meaningful empty/error states. Limit provider fan-out and add per-call deadlines, backoff and an on-demand freshness indicator. The initial customer wedge may keep on-demand reading; background watch/delta is justified only when customers need timely shared inbox operation. Gmail watch requires renewal and history processing [Google watch](https://developers.google.com/workspace/gmail/api/guides/push); Graph supports delta queries [Microsoft delta](https://learn.microsoft.com/en-us/graph/delta-query-messages). Neither should be advertised from the current code.
5. **Privacy and intelligence (P1):** Distinguish native mail from AcreOS campaign email in the UI, then unify the *work queue* across source channels without copying entire inboxes into CRM. A “summarize” or “propose reply” action shows model/provider, what content is sent, and opt-out; an automatic summary requires valid informed authorization. Cache keys include org/account/message and invalidate on disconnect; avoid body text in logs. Treat content as untrusted input; no email instruction can authorize outreach, exports or account changes. Measure summary correctness against actual thread context. The present service summarizes one message, despite its `threadSummary` name.
6. **External MCP (defer send):** Allow a narrowly scoped authenticated tool to list safe metadata or retrieve an authorized message only after the account-binding invariant, customer-controlled scope, abuse limits, and cross-tenant tests. No general `send_email` MCP tool until equivalent product authority, double-send handling, consent and audit are proven. A connector is a provider relationship; MCP is a way to offer tools to an agent.

Benchmark the *experience* against strong modern mail clients' multi-account support and task-focused views [Superhuman account management](https://help.superhuman.com/hc/en-us/articles/46005777934733-Managing-Accounts), [Split Inbox](https://help.superhuman.com/hc/en-us/articles/46005636204941-Custom-Split-Inbox), and real-estate team communication continuity [Follow Up Boss team inbox](https://help.followupboss.com/hc/en-us/articles/4418391260183-Team-Inbox-Overview). These vendor materials show capabilities, not measured superiority. AcreOS's opportunity is linking communication to the investor's asset decision and obligation with higher trust, rather than copying every email-client feature.

## Quality system that prevents another feature avalanche

Give every central feature a **five-part contract** beside its existing route/service, rather than a second product registry:

1. **Job and actor:** Who initiates it, whom it affects, what starts it, the useful end state, and one scenario from scratch and one with existing records.
2. **Evidence:** Field-level origin, date, confidence, rights and missingness; calculated/entered/observed/reconciled states. A calculator can be excellent without a connector if its assumptions are explicit.
3. **Authority and effect:** Read, draft, send, spend, change customer/legal state, export, or notify; permission and confirmation; idempotent recovery for effects.
4. **Operation:** Typical and worst-case volume, bounded payload, external rate/cost, timeout and fallback, freshness, retry, trace to customer-visible status.
5. **Experience:** One primary action, visible result, useful empty/error/recovery states, mobile and accessibility; no incidental details in the first view.

A feature is *customer-complete* when a representative real customer can finish the job, a controlled failure is recoverable, relevant permissions and money claims hold, and support can diagnose what happened. A simulation or test double proves a smaller claim. Use existing `readiness.ts`, provider registry, app intents, event log and founder telemetry; no new universal “feature maturity” database is required. Cross-cutting evidence should be attached to the existing record rather than copied into one monolithic AI memory.

The system should favor **compositional reuse** (common contact/deal/evidence/work/financial primitives) while preserving domain-specific rules. The founder's decision was to finish the existing verticals, not to build every imaginable connector or launch parallel mini-apps. A new provider, autonomous action, or deep feature branch earns its cost when it improves a measured customer job, retention, revenue contribution, risk or support burden. Research products as evidence of a reachable standard, never as a checklist to clone. Modern rental software already couples rent, resident communication, maintenance and reporting [Buildium](https://www.buildium.com/); AcreOS has to make that daily operating loop coherent if it promises to replace outside work for a landlord.

### Onboarding should produce a durable operating shape

The first-run questions should build a **small, inspectable workspace contract** using existing profile, org, permission, data-source and work records. The contract answers: (1) whose business and which role; (2) which strategy/book is active; (3) beginner or existing operation; (4) a real first job; (5) what data is sample, manual or provider-observed; (6) which actions are authorized and by whom. The chosen type should shape vocabulary, default Today queue, first task, relevant empty state, suggested connector and sample example. It should **not** hide a user's real asset because it belongs to a different strategy. A customer changing strategy later changes a view/preference; changing the org's underlying business policy requires explicit owner authority and an explanation of its effect on teammates and existing records.

For **zero-to-one**, use a county/parcel or buyer problem and let the investor reach a bounded preliminary decision without asking for a payment method, list import, or automation authority. For an **existing book**, accept the smallest useful record set and show reconciliation errors before activation: landlord rent roll and unpaid charges; note servicer note schedule and next due; wholesaler leads and contact permissions; tax buyer certificates and verified dates; STR operator reservations and calendars. A useful result is a parcel decision with source limitations, a due payment matched to evidence, a tenant issue assigned to the right actor, or a deadline acknowledged. Creation of a sample record is a setup event. The account may contain multiple strategies; keep the first-screen queue focused on the active job and expose other books through a switch/portfolio view.

Make setup **resumable and idempotent**: kill the browser after each write, reload, reconnect the provider after revoked consent, change note role, invite a teammate, rerun onboarding. For each, show current saved state and one next action. Never advance on a failed required write, and never replay a paid/external effect because the setup UI was retried. Test the exact return behavior on a narrow phone, with screen reader and keyboard, for a new investor and an existing operator. Instrument source-labeled milestones with distinct denominators: signed-up, profile saved, first task viewed, first meaningful decision, first authorized external action accepted, first receipt reconciled, seven-day active. Founder reviews can then ask *where the customer's business failed to progress*, not simply where the wizard lost a click.

| **Grow responsibly** (`growth/campaigns`, `market-reports`, `experiments`, `expansion`) | Segment demand, acquisition cost, activation/retention, contribution and support burden; a test has a bounded audience and stop rule. | A campaign increases signups but yields no first useful job and raises paid-provider cost; the growth view does not call it a win. |

For **founder onboarding**, ask for real operator priorities in stages: expected customer wedge, available support capacity, provider cost ceiling, cohort/feature flags, escalation destination and rollback owner. Present a dry run of a customer joining and an incident being surfaced before enabling external spend or outbound automation. Founder should be able to enter the app after seven days away and answer: *Which customers are stuck? Which money claims are unreconciled? What can the system fix safely? What decision is actually mine?* A gorgeous cockpit that cannot answer those questions is a reporting surface, not an operating experience. Verify the live founder shell and permission model in an authenticated review before moving navigation.

### Scope and stopping point for this research

The existing feature-family matrix plus this transition grid cover the **declared product surface**, but source samples do not amount to a line-by-line proof of every component, every profile, every legal jurisdiction or every third-party integration. A claim of that kind would be false at a repository of this breadth. Further deep reading is justified by a specific failed customer journey, production telemetry or an imminent external launch. The strongest near-term leverage is to make the shared seams truthful and recoverable, then exercise the same contract against each profile. That yields more customer quality per development hour than an indefinitely expanding catalogue of hypothetical features.

## Fourth pass: data rights, risk, event and cost truth

### 8. An unmapped FEMA point becomes “minimal flood hazard”

[`queryFemaFlood`](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/data-source-broker.ts#L1004-L1037) queries a **point** in NFHL layer 28. With an empty feature array, `FLD_ZONE` defaults to `X`, `riskLevel` remains `low`, and the result says `Zone X (Minimal Flood Hazard)` with `source: FEMA NFHL`. Its `lastUpdated` is the lookup instant, not the map's effective date. An explicit mapped X and no result are different evidence states; a point result also cannot rule out a flood-zone intersection elsewhere on a parcel. FEMA describes its National Flood Hazard Layer as covering **more than 90%, not all, of the United States** ([FEMA NFHL](https://www.fema.gov/flood-maps/national-flood-hazard-layer)). Do not turn an empty spatial result, boundary uncertainty, stale map or provider outage into a confident low-risk investment conclusion.

**Acceptance:** Feed empty `features`, an explicit X feature, A/AE, and a malformed/failed response through a controlled double. Empty is `unknown/unmapped`, explicit X is reported with the precise point/map limitation, failed is `unavailable`; only actual zone data supports zone classification. Show lookup time separately from source effective date if supplied. For a parcel decision, state whether boundary geometry was actually checked; if not, require source-map review where material. Reuse existing diligence presentation and provenance types rather than introducing a separate flood engine.

### 9. Broker cache can detach source rights and tier from data

[`generateLookupKey`](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/data-source-broker.ts#L383-L386) uses only category and latitude/longitude rounded to four decimals. [`getCachedResult`](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/data-source-broker.ts#L486-L506) does not use its optional `sourceId` and returns data/time without the source. The [cache hit precedes selection and tier/BYOK qualification](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/data-source-broker.ts#L635-L655), identifying the result simply as `Cache`, tier `cached`, cost zero. ### 10. A paid provider attempt and its credit debit are not one durable event

[`ProviderRegistry.lookup`](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/providers/provider-registry.ts#L191-L202) bypasses the platform credit precheck when a BYOK key **row is present**. If resolution fails, it [falls back to the platform key and billing](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/providers/provider-registry.ts#L258-L276) without repeating the balance/choice gate. On a successful paid lookup, the [credit debit is started without awaiting](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/providers/provider-registry.ts#L299-L313). Its [idempotency key uses input fingerprint plus UTC day](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/providers/provider-registry.ts#L627-L657): two genuinely paid identical vendor requests in one day can collapse to one credit row. The [post-hoc record mode](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/creditPool.ts#L452-L464) returns `allowed:true` and zero debit on database failure; the caller does not inspect that result. Provider-intelligence telemetry is a separate attempted observation, so this finding specifically concerns customer credit/financial reconciliation, not proof that all cost telemetry is missing.

**Acceptance:** Two noncacheable paid vendor calls with identical input on the same day produce two distinct provider attempts and two matching ledger events; replay of one attempt produces one. A broken BYOK key cannot unexpectedly consume platform credits without applying the actual eligibility and disclosed billing path. Force the debit database to fail after provider success: retain an unresolved, reconcilable cost obligation and show it to founder/affected customer as appropriate. An ambiguous vendor outcome must not be charged again by an unexamined retry. Use a durable attempt identity at this boundary; do not precharge every hypothetical lookup or build a new billing platform.

### 11. An unavailable workflow action can be reported as a completed run; emitted events live in process memory

[`WorkflowEngine.emit`](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/services/workflow-engine.ts#L1957-L1984) pushes into a process-local array, starts processing without awaiting it, and catches event processing errors. A compliance-blocked send may intentionally permit independent later work; an unavailable send that is prerequisite to later customer-facing actions needs an explicit dependency rule and honest aggregate status. The existing persisted delayed-run handling should remain.

**Acceptance:** Simulate a missing connected mail identity for a workflow with `send_email` followed by an action requiring that send. The send is unavailable, the dependent action does not assert communication occurred, and run/Today/founder status says incomplete or completed with exception rather than plain success. An independent later action can still run under declared policy. Inject process termination after a servicing ledger commit: the owed receipt/notice trigger is recovered once from a transactional outbox or ledger reconciliation, without double-send on replay. Qualify the bounded customer-important triggers first, not every low-stakes event.

### 12. Founder “MRR” is trailing revenue and can activate cost recommendations

[`computeTrailing30dMrrCents`](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/routes-finance-ledger.ts#L59-L71) sums every `financialLedger.category = revenue` row in the last 30 days. The [MRR endpoint](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/routes-finance-ledger.ts#L138-L193) labels that sum `currentMrr`, and the [active scale-up recommendations](https://github.com/Thmsnrtn/AcreOS/blob/a2dc971809df64e2e10d8c3e1f1d3f1cc2496a31/server/routes-finance-ledger.ts#L435-L484) compare it to fixed MRR thresholds. **Acceptance:** Seed one-time revenue, recurring charges, refund and a terminated subscription with known dates. Recommendations are advisory until founder authorization, and their crossing date is only asserted if historically observed.

### Synthesis: what this changes in the mature product

The shared operating contract should carry **source and rights**, **observation time and coverage**, **effect/attempt identity**, **financial status**, **obligation**, and **recovery state** across profile surfaces. These are fields and transition rules at existing chokepoints, not a demand for a universal new event platform. In customer UI, a parcel risk card should be allowed to say “not established”; a provider purchase must have an accountable cost; a workflow should not congratulate the user on an action it could not do. In founder UI, recurring revenue and durable obligations should be distinct from posted revenue and successful-looking logs. This advances the apparently effortless experience because the system can carry honest uncertainty and recover routine failures without asking the user to infer what happened.

### Consequence for the directive
